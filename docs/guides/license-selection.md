本文档帮助维护者在公开仓库前完成许可证决策和落地检查，不提供法律意见，也不使用占位文本冒充有效许可证。对商业授权、双重许可、专利、商标或复杂依赖有疑问时，应咨询具备资质的专业人士。

初始化器生成的 open-source profile 只是**开源准备态脚手架**。在 § 4 落地真实许可证文本并完成 § 6 检查前，不应把项目标记或发布为已获得开源授权。

## 1. 必须先确认的事实

- 公开代码仓库不等于已经授予开源使用权。没有明确许可证时，使用、修改和再分发通常仍受默认版权规则限制。
- 只有维护者有权处置、或已经获得授权的代码和资源，才能纳入许可证范围。
- 依赖、复制代码、模型、字体、图片、数据集和文档可能具有不同许可证，必须分别核对。
- “source available”或带额外用途限制的许可不一定属于 OSI 定义下的开源许可证。

权威入口：

- [OSI Approved Licenses](https://opensource.org/licenses)
- [SPDX License List](https://spdx.org/licenses/)
- [GitHub：Licensing a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)

## 3. 选择时的检查维度

| 维度 | 需要回答的问题 |
|------|----------------|
| 使用与分发 | 是否允许商业使用、修改、再分发和私有使用？ |
| 互惠要求 | 修改或衍生作品是否必须以相同许可证公开？范围是什么？ |
| 专利条款 | 是否存在明确的专利授权、终止或报复条款？ |
| 通知义务 | 分发时需要保留哪些版权、许可证或 NOTICE 内容？ |
| 依赖兼容性 | 直接依赖、复制代码和打包产物的许可证是否兼容？ |
| 贡献模式 | 外部贡献采用同一许可证、DCO、CLA，还是其他约定？ |
| 组织约束 | 雇主、客户、学校、资助方或合同是否限制授权权利？ |

不要仅凭“宽松”“强 copyleft”等标签做决定；最终应阅读所选许可证的完整正文和适用条件。

## 4. 落地步骤

1. 从 OSI / SPDX 等权威来源确认许可证名称、SPDX 标识和完整文本。
2. 将完整、未经随意改写的许可证文本保存为仓库根目录 `LICENSE` 或许可证要求的标准文件名。
3. 按许可证正文要求填写版权年份、主体或其他允许替换的字段。
4. 在项目 `README.md` 和包元数据中填写同一个 SPDX 标识。
5. 需要保留第三方声明时，新增 `NOTICE` 或 `THIRD_PARTY_NOTICES`，并列出来源和许可证。
6. 在 `CONTRIBUTING.md` 中说明外部贡献采用的授权方式。
7. 运行发布检查，确认源码包、二进制包和容器镜像包含必须分发的许可证与通知文件。

## 5. 不应自动化的行为

- 不根据项目名称、公开状态或技术栈自动替维护者选择许可证。
- 不生成 `LICENSE` 占位文件并声称项目已经开源。
- 不删除第三方版权、许可证或 NOTICE 内容。
- 不把代码许可证自动套用于字体、图片、数据集、模型或商标。
- 不在不理解影响时自行拼接多个许可证或附加限制。

## 6. 发布前检查清单

- [ ] 已明确记录许可证 SPDX 标识和决策人。
- [ ] 仓库根目录存在真实、完整的许可证文件。
- [ ] README、包元数据和 LICENSE 的许可证标识一致。
- [ ] 项目有权授权全部纳入范围的自有内容。
- [ ] 第三方依赖和复制内容已完成兼容性与通知义务检查。
- [ ] 外部贡献的授权方式已在贡献指南中写清。
- [ ] 商标、数据、模型和素材等非代码资产已单独确认。
