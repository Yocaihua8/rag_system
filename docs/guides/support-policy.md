# 支持范围

> 状态：Active
> Owner：RAG 团队
> Last Updated：2026-07-30
> Scope：Knowledge Island 当前维护版本的公开支持范围、渠道、优先级和升级边界
> Related：`troubleshooting.md`、`runbook.md`、`security.md`、`../../SECURITY.md`、`../../CONTRIBUTING.md`、`../BACKLOG.md`

Knowledge Island 当前由小规模维护者以尽力方式维护，没有商业支持合同、7×24 值班或承诺 SLA。本文件描述问题如何进入维护流程，不承诺固定响应或修复时间。

## 1. 支持对象

| 对象 | 是否支持 | 说明 |
|------|----------|------|
| 项目维护与开发人员 | 是，尽力支持 | 当前代码、测试、构建、文档和发布流程内的问题 |
| 外部贡献者 | 是，尽力支持 | 通过公开 Issue / PR 讨论可复现问题和贡献；许可证未决边界见 `license-selection.md` |
| 个人使用者 | 是，尽力支持 | 正式发布版本和当前文档覆盖的安装、配置、导入、检索与问答问题 |
| 商业客户 / 合作方 | N/A | 当前没有已记录的商业支持合同或专用渠道 |
| 自定义分支或二次开发 | 有限 | 可协助定位上游行为；不承诺维护第三方修改、私有基础设施或定制集成 |

## 2. 支持渠道

| 渠道 | 适用场景 | 是否公开 | 负责人 |
|------|----------|----------|--------|
| GitHub Issue | Bug、功能建议、文档问题、一般配置风险 | 是 | RAG 团队 |
| Pull Request Review | 对仓库代码、测试或文档的贡献 | 是 | CODEOWNERS / 被指定 Reviewer |
| 私密安全报告 | 可利用漏洞、密钥或敏感数据泄露 | 否 | 入口 TBD；安全负责人 TBD |
| 行为规范私密报告 | 骚扰、隐私或社区行为问题 | 否 | 入口和处理人均 TBD |
| 即时沟通群 / 值班渠道 | 紧急协调 | N/A；当前未建立 | N/A |
| 商务 / 客户支持渠道 | 合同支持 | N/A；当前未建立 | N/A |

公开 Issue 不得包含漏洞利用细节、Token、API Key、完整私密文档或个人信息。私密入口未建立前，只能在公开 Issue 中说明最小风险摘要并请求维护者提供私密联系方式。

## 3. 优先级与响应边界

| 级别 | 适用情况 | 首次响应目标 | 处理目标 |
|------|----------|--------------|----------|
| P0 | 可利用安全风险、明确数据破坏风险、当前主流程完全不可用 | TBD；无承诺 SLA，发现后尽快分流 | 先限制影响，再评估修复或回退 |
| P1 | 导入、检索、问答或正式发布安装链路中的重要功能不可用 | TBD；无承诺 SLA | 复现、确认范围并给出修复或临时规避 |
| P2 | 局部功能异常，存在明确规避方式 | TBD；无承诺 SLA | 纳入 BACKLOG 并按优先级处理 |
| P3 | 咨询、文档建议、低风险体验改进 | TBD；无承诺 SLA | 视维护能力答复或记录 |

优先级由影响范围、可复现性、数据 / 安全风险和是否存在规避方式共同决定。提交者标注的级别不是最终结论。

## 4. 支持范围

支持事项：

- `v2.0.0` 正式发布版本与当前 `main` 的可复现缺陷。
- 文档列出的本地 Web、Docker、Tauri Windows 和 Obsidian Bridge 使用问题。
- 已实现 API、配置、数据代际和迁移边界的澄清。
- 文档缺口、示例错误和可验证的代码 / 文档不一致。
- 安全问题的接收、评估和修复协调；私密入口完善前存在已知流程缺口。

不在承诺范围内：

- 历史 Tag 的常规维护或安全修复；`SECURITY.md` 当前要求升级到最新维护状态。
- macOS / Linux v2 原生包支持；v2.0.0 本轮未生成或验证这些原生产物。
- Windows NSIS 的 Authenticode 签名保证；v2.0.0 发布资产明确为未签名。
- 用户自行改变监听地址、网络映射、依赖版本或源码后的环境兜底。
- 第三方 LLM / Embedding Provider、Docker、操作系统、Obsidian 或 GitHub 的可用性、配额与服务时效。
- 数据恢复成功保证；当前整库备份脚本存在 v2 默认路径漂移，且没有经验证的自动恢复链路。
- 商业 SLA、合规认证、法务意见或 7×24 值班。

## 5. 维护版本

| 版本 / 分支 | 状态 | 支持结束时间 | 说明 |
|-------------|------|--------------|------|
| `main` | Active development | TBD | 当前维护源；未发布提交不等同于稳定版本 |
| `v2.0.0` | Current release | TBD | 2026-07-30 正式发布；Windows x64 NSIS 未签名 |
| v2.0.0 之前的历史 Tag | End of Life | 已结束 / N/A | 不提供常规支持或安全修复，使用者应升级 |
| macOS / Linux v2 原生包 | N/A | N/A | 当前未生成或验证 |

项目没有已确认的 LTS、多版本并行维护或固定弃用周期。未来改变支持窗口时，必须同步 `SECURITY.md`、README、CHANGELOG 和发布说明。

## 6. 提交问题所需信息

公开问题至少应包含：

- 使用的版本号或 commit SHA。
- 运行方式：本地 Web、Docker、Tauri 或 Obsidian Bridge。
- 操作系统、Python / Node 版本，以及与问题相关的配置名称；不要附凭证值。
- 最小复现步骤、预期结果和实际结果。
- 脱敏后的完整错误文本与发生时间。
- 是否影响 `runtime/v2/` 数据、是否可在隔离数据目录复现。
- 已尝试的排查步骤。

缺少信息时维护者可以请求补充，但不能因问题描述不完整而诱导用户公开敏感内容。

## 7. 安全问题入口

- 一般安全建议或配置风险可以提交公开 Issue。
- 可利用漏洞、密钥、Token、个人信息或完整攻击路径不得发布在公开 Issue。
- 当前可确认的私密邮箱、GitHub Security Advisory 入口和安全负责人均为 TBD。
- `SECURITY.md` 中写明了私信 / Email 方向，但未给出具体地址；在入口补齐前不应宣称已经建立完整私密响应渠道。
- 本项目没有保证性安全响应 SLA；实际处理以风险、维护能力和可用负责人为准。

## 8. 升级与回流

| 场景 | 升级对象 | 需要材料 |
|------|----------|----------|
| 无法复现但影响持续 | RAG 团队 | 脱敏日志、时间范围、版本、运行方式和已尝试步骤 |
| 疑似安全问题 | 安全负责人 TBD；技术缓解由 RAG 团队承担 | 私密报告、影响版本、复现步骤和泄漏凭证范围 |
| 数据损坏或恢复请求 | RAG 团队 | 实际 `RAG_RUNTIME_DIR`、备份来源、是否停止应用、文件哈希和错误日志 |
| 涉及合同、报价或合规 | N/A / 项目 Owner TBD | 当前无商业流程；需先建立合同和责任边界 |
| 涉及架构决策 | 仓库维护者 | RFC / ADR 草案、替代方案、兼容与回滚影响 |

- 可复现缺陷或长期改进写入 `docs/BACKLOG.md`。
- 常见故障的稳定排查步骤回流到 `troubleshooting.md` 或 `runbook.md`。
- 造成较大影响且需要根因分析的问题，在 Issue 或 PR 中建立可追踪复盘并关联修复提交。
- 只有产生独立架构决策时才新建 ADR。
