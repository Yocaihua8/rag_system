## 2. 功能目标

项目知识教练把当前项目的代码、文档和笔记转为可验证的学习对象，帮助用户完成：

```text
项目输入 -> 有来源的理解 -> 学习问答 -> 项目评估
        -> 知识覆盖与技能差距 -> 学习计划 -> Obsidian 发布
```

主评价对象是“用户对当前项目知识的理解”。通用技能树只用于归类和组织学习差距，不构成跨项目能力档案、职业能力分数或求职评价。

## 3. 核心业务对象

| 对象 | 业务含义 |
|------|----------|
| 项目 | 一组相互隔离的代码、文档、笔记及教练数据；界面称“工作区” |
| 来源 | 支撑结论的真实文件、片段或导入记录 |
| 分析运行 | 针对某一来源版本生成项目理解的过程，可为最新或 `stale` |
| 知识点 | 用户需要理解的项目事实、流程、约束或代码定位，具有稳定标识和来源 |
| 技能节点 | 语言、框架、数据、测试、交付、AI 等通用学习主题 |
| 评估会话 | 针对知识点或技能节点的一组可恢复问题、回答和结果 |
| 学习计划 | 从项目差距生成、可编辑并由用户确认的版本化任务列表 |
| Obsidian 发布 | 经预览和确认后由插件写入系统管理 Markdown 的不可变修订 |

## 4. 项目分析契约

### 4.1 分析策略

- B-161 已对 Python、JavaScript / TypeScript、`package.json`、`pyproject.toml`、requirements、TypeScript / Vite、Docker / Compose 等常见清单启用首批专门规则。
- 其他文本项目使用已入库的 README、目录和高信号文档通用回退；分析器不绕过导入层直接扫描磁盘。
- 无 LLM 时，规则基线已经能够生成基础项目概览、稳定知识点和有来源的技能映射。
- 有 LLM 时，B-161 只允许增强项目概览摘要；知识点、技能映射和来源仍由规则确定。模型失败返回规则结果和 warning。

### 4.2 来源规则

- 每个项目结论、知识点和技能映射必须至少关联一个真实来源。
- B-161 存储层要求来源解析到同项目已导入文档或分块，并以数据库中的相对路径和 checksum 为准，拒绝调用方伪造路径或哈希。
- 没有足够来源时，结果必须标记未知或省略，不得由模型补造。
- 来源内容变化或删除后，相关分析必须标记为 `stale`。
- 来源重命名应保留文档映射；删除来源应清理对应索引。
- 重新分析生成新运行，不静默改写历史分析、评估或已确认计划。
- B-161 已在文档新增、修改、删除及 GET 指纹复核时把受影响分析标为 `stale`；来源快照在原文档删除后仍保留相对路径、哈希、摘录和定位。

## 5. 评估与覆盖契约

### 5.1 发起与作答

- 评估可从知识点、技能节点或教练输入工具发起。
- 评估会话必须持久化并可恢复，不固定使用第一份文档或固定三道题。
- 作答前只返回题目和必要上下文，不返回参考答案、评分关键词或评分依据。
- 作答后记录 `rule|model` 评估方式、分数、置信度、命中证据、缺失点和来源。
- 模型不可用或结果不可验证时回退为规则评估，并明确低置信度。
- `evaluation_mode` 只允许 `auto / rule`；相同题目和相同规范化答案可幂等重放，不同答案不得覆盖已保存结果。
- B-162 对同一分析运行、目标类型和目标 ID 只保留一个活动会话；重复发起恢复原会话，`restart=true` 会放弃旧活动会话并创建新会话。
- 知识点目标生成一题；技能目标按当前项目映射置信度选择最多三个知识点。来源或项目指纹变化后，历史会话仍可只读恢复，但不能继续作答。
- 模型评分必须完整覆盖服务端评分点，命中证据必须逐字出现在用户回答中；无效模型结果仅将本题的本次作答回退规则评分，置信度不高于 `0.49`。

### 5.2 状态与阈值

| 状态 | 规则 | 用户含义 |
|------|------|----------|
| `unassessed` | 没有有效评估 | 尚未验证 |
| `needs_work` | 得分 `< 0.50` | 当前项目中需要补强 |
| `developing` | 得分 `0.50–0.74` | 当前项目中正在形成理解 |
| `mastered` | 得分 `≥ 0.75` | 当前项目中已有较充分证据 |

所有界面必须说明：结果只代表当前项目、当前来源版本下的评估，不代表用户整体技术能力。

### 5.3 双层差距

- 项目知识覆盖是主视图，逐知识点展示状态、来源和最近评估。
- 通用技能树是辅助视图，状态只由关联项目知识点聚合。
- “未验证”不得与“评估较弱”合并。
- 技能节点没有知识点映射时保持无项目证据，不得判断为掌握或缺失。
- B-162 技能聚合状态使用 `no_project_evidence / unverified / partially_verified / verified`；只对已验证知识点按映射置信度加权，不把未作答知识点当作低分。
- `confidence < 0.65` 的结果标记为低置信度；低置信度与掌握状态分开表达。
- 覆盖率是“当前来源版本下已有有效评估的知识点数 / 知识点总数”，不是平均分或掌握率。分析过期后旧结果只作为历史结果展示，当前知识点恢复为 `unassessed`。
- 禁止输出跨项目总分、职业等级、JD 匹配、求职建议、绩效或排名。

## 6. 学习计划契约

- 计划由当前项目知识覆盖生成，技能节点只作为任务的辅助关联。
- 普通 `learning` 任务必须包含目标、关联知识点或技能、真实阅读来源、练习问题、完成标准、预计时长和状态；`source_gap` 任务明确没有阅读来源。
- 草稿可编辑和排序，确认后形成独立版本。
- 再次生成只创建新草稿，不覆盖已确认计划。
- 来源不足时可以生成“补充资料”任务，但不得伪造阅读来源。
- B-162 默认最多生成 8 项、上限 20 项；顺序固定为 `needs_work`、`developing`、`unassessed`，同级按分数和知识点 `stable_key` 排序；全部知识点为 `mastered` 时不伪造任务。
- 只有项目最高 revision 计划仍为 `draft` 时，该草稿才可以编辑结构或确认；更早草稿只读保留。草稿结构更新采用完整任务列表和列表顺序，任务状态强制回到 `todo`。
- 确认后任务结构、排序、关联与来源冻结，只允许将进度更新为 `todo / in_progress / done / skipped`；新确认版本会把旧确认版本归档。
- 计划响应同时提供结构哈希和进度哈希，用于阻止过期页面静默覆盖；历史计划的阅读来源按其 `based_on_run_id` 解析，不替换为新分析来源。
- 过期分析禁止生成、编辑结构和确认新计划，但已确认计划仍可继续更新任务进度。
- 确认学习计划不等于发布；发布到 Obsidian 仍需单独预览和确认。
- 首版不提供日历排期、提醒、自动执行或证书。

## 7. Obsidian 协作边界

### 7.1 输入（B-163 已实现）

- 现有 `/api/import/obsidian-vault` 保持一次性只读导入语义。
- 2.0 通过 `integrations/obsidian-plugin/` 独立桌面插件接收 `upsert / rename / delete` 幂等事件；插件使用 Vault 事件、Frontmatter 和链接元数据 API，不支持移动端。
- 插件可以发送 Frontmatter、标签、已解析和未解析 Wikilink；系统管理输出目录不反向摄入。
- 每个项目最多一个活动连接；一次性配对码限时有效，换取的插件令牌可撤销，服务端只保存配对码和令牌哈希。

### 7.2 输出（B-163 已实现）

默认发布目录为 `Knowledge Island/<项目名>/`，可在配对时修改。目标产物包括：

- `项目理解.md`
- `知识覆盖与技能差距.md`
- `学习计划.md`
- `评估记录/<时间>.md`

发布必须经过“内容与路径预览 → 用户确认 → 插件执行 → 结果回传”。确认只把不可变发布修订置为 `queued`，只有插件回传后才进入 `applied / conflict / failed`。可更新文件必须带 `knowledge_island_managed`、稳定 ID、项目 ID、产物类型和修订号。

以下情况必须停止覆盖并返回冲突：

- 目标文件没有系统管理标记。
- 文件哈希自上次修订后变化。
- 目标路径超出授权输出目录。
- 插件离线、令牌失效或项目连接已撤销。

首版不自动合并冲突。被用户删除的生成文件不自动重建；系统保留不可变发布修订和结果用于追溯。回滚从历史发布内容创建新的修订，并重新经过确认和插件执行，不原地修改历史记录。

## 8. Vue 体验契约

- B-164 已把一级入口切换为“教练 / 学习地图 / 学习计划 / 资料 / 设置”；“教练”继续复用 Codex 风格侧栏、会话、流式回答和原回答依据抽屉。
- “学习地图”展示项目理解、知识覆盖、技能差距和最近评估。项目结论、知识点、技能映射、评估证据和计划阅读项统一通过来源抽屉查看真实路径、摘录与定位。
- 定向评估使用覆盖层，从教练输入工具或学习地图节点进入；作答前不展示评分依据，提交后展示状态、方式、置信度、命中证据、缺失点和来源。关闭覆盖层不会切换当前页面或项目。
- “学习计划”支持生成新草稿、编辑任务内容、上下排序和确认；确认版只开放任务进度更新。发布到 Obsidian 需要另外打开内容与路径预览并再次确认。
- “资料”弹窗展示当前项目真实 Obsidian 连接和同步状态，并把插件持续连接与原有 Vault 路径“一次性只读导入”明确分开。
- “设置”提供当前项目 Obsidian 连接读取、一次性配对码、输出目录和令牌撤销。浏览器不会持有插件令牌，也不调用插件专用的待执行领取、同步事件或结果回传路由。
- 发布确认后界面显示 `queued / 等待插件执行`，不把用户确认伪装成 Vault 已写入；`applied / conflict / failed` 以插件后续回传为准。
- 高级检索、模型比较和 Agent 审计继续收在高级区域；旧 `AssessmentView` 与 `/api/assessment/*` 仅保留兼容，新前端闭环使用 Coach API。

## 9. 数据与兼容契约

- 2.0 默认数据根为 `runtime/v2/`，用户需要重新导入项目。
- 不提供 1.x 数据迁移、合并或跨项目能力汇总。
- 旧 `runtime/app.db`、向量目录和输出保持原样。
- 现有导入、聊天和 `/api/assessment/*` 契约继续保留；新闭环使用 Coach 和 Obsidian API。
- 敏感令牌、API Key 或密码不得明文持久化或在普通响应中返回。

## 10. 验收标准

- Python、JavaScript / TypeScript 和通用文本样例都能生成有来源的项目理解。
- 未配置 LLM 时规则基线可完成分析、评估、差距和计划；LLM 失败时可受控回退。
- 知识点定向评估可恢复，评分依据在作答前不可见，结果包含评估方式、置信度、证据、缺失点和来源。
- 项目覆盖与技能树正确区分 `unassessed` 和低分状态，并展示“仅限当前项目”的说明。
- 新计划草稿不覆盖已确认版本。
- Vue 五入口、来源抽屉、定向评估覆盖层、学习计划草稿编辑/排序/确认与确认版进度更新均可通过前端单元测试和静态契约验证。
- 资料与设置能区分一次性只读导入和插件连接；发布确认后只显示 `queued`，等待插件执行，不在浏览器调用插件专用路由。
- Obsidian 重复事件、重命名、删除、离线重放和输出目录排除有确定行为。
- 发布可完成预览、确认、执行和结果回传；无标记文件、哈希冲突和路径越界均被阻断。
- 端到端闭环通过后，旧运行时目录仍保持不变。

B-165 已通过包含同步/流式问答、计划编辑与确认、四类 Obsidian 产物和插件结果回传的完整闭环测试。命令、数量、旧运行时哈希和原生工具链边界见 `docs/release/V2_0_0_READINESS_2026-07-24.md`。

## 11. 非目标

- 团队空间、多用户、云同步、跨项目知识或能力汇总。
- 职业能力、JD 匹配、求职评价、绩效考核或个人排名。
- 移动端、Obsidian 移动插件或社区市场发布。
- 完整 AST 调用图、全语言静态分析、IDE 或 Agent 编码。
- 日历排期、提醒、证书和无需确认的自动发布。
- 修改无系统管理标记的 Obsidian 用户笔记。
