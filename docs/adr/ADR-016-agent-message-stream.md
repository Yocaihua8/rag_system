# ADR-016 持久任务消息与可重放 Agent 消息流

> 状态：Accepted
> Date：2026-08-02
> Owner：RAG 团队
> Scope：v3 任务消息、实时回答事件和前端展示投影的职责边界
> Related：`../features/agent-tasks-and-runs.md`、`../design/agent-runtime-and-tool-contract.md`、`../design/api-spec.md`、`ADR-013-durable-dag-executor.md`、`ADR-015-v3-data-api-storage.md`

## 1. 背景

当前 v3 alpha 已能持久化任务消息和 Run 事件，并通过 SSE 按 sequence 回放运行状态，但没有 Agent 回答的 started/delta/completed 事件。未通过评审的 P1 横屏原型把排队、运行、审批、恢复和完成等互斥状态同时摆在时间线中，发送后也只有本地用户气泡，无法表达真实的服务端接受、分段回答、断线恢复和终态。

如果把临时分块直接当作会话历史，刷新后容易出现重复、缺段或半条消息；如果只保存完整回答，实时界面又无法可靠恢复。还需要防止前端按钮自行推断任务已完成、已批准或已取消。

## 2. 决策结论

- `agent_task_messages` 保存长期会话事实。用户首消息与 Task 在同一事务创建；Agent 回答完成或中断后，以完整内容或明确标记的可见部分内容保存为任务消息。
- `agent_events` 保存只追加的运行事实和语义分块。回答使用 `assistant.message.started / delta / completed / interrupted`，并沿用 Run 内单调递增的 `sequence`。
- delta 按句子或短段聚合，使用稳定 `message_id` 与 `chunk_index`；不得为了模拟流式效果把已有完整结果故意延迟输出，也不按单 token 持久化。
- 状态变化、最终任务消息和终结事件按用例要求在同一事务提交。幂等执行不得为同一回答创建第二组消息或重复分块。
- 新页面以持久任务消息恢复已完成历史，以 Run 事件恢复正在生成的回答。`Last-Event-ID` 或 `after_sequence` 用于续传，客户端忽略不大于最后已消费 sequence 的事件。
- 前端 reducer 只把服务端消息、运行、步骤、审批、产物事件和本地命令提交状态投影为界面。点击按钮只能进入“提交中”，不能乐观写入最终业务状态。
- P1 Revision 2/3 使用确定性的演示状态机验证这套投影合同，但不调用真实 API；P1 演示通过不等于 v3 后端或 React 生产前端已完成。

## 3. 决策原因

1. 完整消息适合长期读取、搜索和刷新恢复，append-only 事件适合实时传输、审计和断点续传。
2. 语义分块比逐 token 事件更易阅读，也能控制 SQLite 写入量。
3. 服务端事件作为业务状态事实源，可以避免审批、取消、失败恢复和产物状态在多个客户端中分叉。
4. reducer 投影可用相同事件序列重放界面，便于测试断线、重复事件和中断回答。

## 4. 备选方案

### 4.1 只保存完整消息，不保存分块事件

- 优点：存储和读取最简单。
- 缺点：无法表达生成中的回答，断线后只能重新请求完整内容。
- 未采用原因：不能满足持久 Run 的实时反馈与续传要求。

### 4.2 每个 token 都作为任务消息保存

- 优点：客户端实现表面上简单。
- 缺点：破坏消息原子性，写入量大，刷新时难区分临时片段和完整历史。
- 未采用原因：不适合 SQLite 本地优先产品，也不利于审计和恢复。

### 4.3 前端本地拼接并乐观推进业务状态

- 优点：按钮响应看起来更快。
- 缺点：请求失败、重复提交或断线时容易显示错误终态。
- 未采用原因：违反后端作为执行、审批和权限事实源的边界。

## 5. 影响

### 5.1 正面影响

- 会话历史、实时回答和运行审计各自有单一职责。
- SSE 重连可以无重复地继续当前回答。
- P1、未来 React 前端和后端测试可共享同一状态投影合同。

### 5.2 负面影响

- executor 需要维护稳定消息 ID、分块序号、内容哈希和中断语义。
- 前端必须实现 reducer、去重和滚动跟随，不能仅靠请求回调切换页面状态。
- 调试时需要同时检查任务消息与事件序列。

### 5.3 对现有系统的改动点

- B-178 为 `/api/v3` 增加任务首消息响应、运行输入消息引用和 Agent 消息事件。
- 固定项目检查工作流目标版本增加安全回答节点；通用自然语言澄清仍只属于 P1 演示合同。
- 不修改 v2 Vue、`/api/v2` 或 v2 数据，不以 P1 演示数据作为运行回退。

### 6.2 回滚策略

| 项目 | 内容 |
|------|------|
| 回滚触发条件 | 消息重复、缺段、任务消息与终结事件不一致或 SSE 续传回归 |
| 回滚步骤 | 停用新回答节点和 `assistant.message.*` 发出路径，恢复仅返回既有任务消息与运行事件的 alpha 行为；保留诊断数据 |
| 数据回滚说明 | 不自动删除已保存的任务消息或事件；通过修复读取投影兼容已存在记录 |
| 回滚责任人 | RAG 团队 |
| 不可回滚的点 | 已被用户读取或导出的回答无法收回 |

### 6.3 验证方式

- 验证指标：消息/事件一致性、重复分块数、SSE 续传完整性、终态错误投影数。
- 观察窗口：B-178 定向测试与 P1 Revision 2/3 评审期间。
- 验收标准：started 到 completed/interrupted 顺序稳定；重连无重复；刷新后历史与事件重放一致；客户端不自行产生业务终态。
