# 开源项目治理

> 状态：Active
> Owner：RAG 团队
> Last Updated：2026-07-30
> Scope：Knowledge Island 公开仓库的参与方式、决策权限、分歧处理与维护者交接
> Related：`../../CONTRIBUTING.md`、`../../CODE_OF_CONDUCT.md`、`../../SECURITY.md`、`support-policy.md`、`license-selection.md`、`../BACKLOG.md`

本文档定义公开仓库中的协作和决策边界。仓库当前没有 `LICENSE`，因此“公开可见”不等于已经授予开源使用、修改或再分发权；许可证状态以 `license-selection.md` 为准。

## 1. 项目治理范围

| 项目 | 当前约定 |
|------|----------|
| 项目使命 | 将本地文档转化为可检索的项目知识，并通过来源约束的检索、问答和学习闭环帮助个人或小团队使用知识 |
| 治理范围 | 仓库代码、文档、Issue、Pull Request、发布、社区行为和安全协调 |
| 主要沟通渠道 | GitHub Issue 与 Pull Request；私密安全和行为报告入口均为 TBD |
| 决策记录位置 | 功能范围写入 `docs/features/`，架构决策写入 `docs/adr/`，任务与技术债写入 `docs/BACKLOG.md`，执行计划写入 `docs/plans/`，实际合并结论保留在 PR |
| 当前维护模式 | 单维护者主导；`.github/CODEOWNERS` 当前默认 Owner 为 `@Yocaihua8` |

## 2. 角色与权限

| 角色 | 职责 | 可执行操作 | 产生方式 |
|------|------|------------|----------|
| 仓库维护者 | 路线图、合并、发布、安全协调和权限管理 | 管理 Issue / PR、合并变更、创建 Tag / Release、管理仓库配置 | 当前由 `@Yocaihua8` 承担；新增或替换规则为 TBD |
| Reviewer | 评审被指派的模块或主题 | Review、提出阻塞问题、建议合并或退回 | 由仓库维护者按变更范围临时指定；当前无固定 Reviewer 名单 |
| 贡献者 | 提交 Issue、代码、文档或测试 | 按 `CONTRIBUTING.md` 发起贡献 | 完成被接受的贡献；许可证未决期间，贡献授权条款仍需书面明确 |
| 使用者 | 使用已发布版本并反馈问题 | 提交 Issue 或参与公开讨论 | 无需额外仓库权限 |

代码托管权限只是执行手段，不等同于永久治理权。维护者和 Reviewer 发生变化时，应同步更新 `.github/CODEOWNERS` 和本文件。

## 3. 决策方式

| 决策类型 | 默认方式 | 决策人 | 记录位置 |
|----------|----------|--------|----------|
| 小型修复与文档调整 | 按仓库 plan / BACKLOG 规则实施，完成验证后通过 PR 合并 | 仓库维护者或被指定 Reviewer | BACKLOG / plan + PR |
| 新功能与行为变化 | 先在功能文档和 BACKLOG 明确范围，再实现、测试和 Review | 仓库维护者 | 功能文档 + BACKLOG / plan + PR |
| 重大架构或兼容性变化 | 按 `AGENTS.md` 的确认边界评审 RFC / ADR | 仓库维护者；其他决策参与人 TBD | RFC + ADR + PR |
| 安全事件 | 通过已确认的私密渠道协调；当前私密入口 TBD | 安全负责人 TBD；技术缓解由 RAG 团队执行 | 私密事件记录；修复后按需公开 |
| 许可证或治理变化 | 提交可审查的文档变更；评议时长和额外批准规则 TBD | 有权授权的项目维护者 | Governance / License PR |

当前治理不承诺全员共识或固定评议周期。事实、备选方案、影响范围和最终结论必须可追踪。

## 4. 分歧与升级路径

1. 在原 Issue 或 PR 中明确争议点、事实依据、可选方案和不做事项。
2. 由对应模块 Owner 或当前仓库维护者给出初步结论。
3. 涉及跨模块、兼容性、安全、许可证或社区规则时，升级给仓库维护者；其他核心维护者当前为 TBD。
4. 暂时无法决策时，在 BACKLOG 或 plan 中记录阻塞原因、重新评估条件和负责人，不虚构截止日期。
5. 行为规范或安全问题不得在公开线程披露受害者信息、密钥或未修复漏洞细节；私密入口未建立前应只公开最小必要信息。

当前没有独立治理委员会或外部仲裁机制。单维护者利益冲突、本人被投诉或账号失联时的替代决策人均为 TBD，这是已知治理单点风险。

## 5. 维护者加入、退出与继任

| 场景 | 当前规则 |
|------|----------|
| 新增维护者 | 资格周期、贡献门槛和批准人数均为 TBD；在规则确定前由当前仓库维护者逐案书面确认 |
| 权限扩大 | 先限定目录、Review 或发布权限，明确复核条件后再扩大 |
| 主动退出 | 交接未完成事项、仓库权限、Tag / Release 权限、安全报告和恢复方式，并更新 CODEOWNERS |
| 长期不活跃 | 不活跃期限为 TBD；发现无人响应时在 README 和 Issue 中明确维护状态 |
| 紧急撤权 | 账号泄漏、权限滥用或明确安全风险时可先撤权，再记录原因和复核结论 |
| 项目无人维护 | 在 README 标明维护停止或归档状态，停止发布；继任人及转移条件为 TBD |
