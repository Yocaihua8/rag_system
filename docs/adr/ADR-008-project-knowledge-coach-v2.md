# ADR-008 项目知识教练与 v2 数据代际

> 状态：Accepted
> Date：2026-07-23
> Owner：RAG 团队
> Scope：项目知识教练产品主线、Coach 领域模型与 v2 数据代际
> Related：[项目知识教练](../features/project-knowledge-coach.md)、[系统设计总览](../design/system-design-overview.md)、[数据库设计](../design/database-design.md)、[状态流与验收](../design/state-flow-and-acceptance.md)、[BACKLOG](../BACKLOG.md)

## 1. 背景

Knowledge Island 1.x 已形成以本地资料导入、RAG 检索问答和轻量评估为主的 Web MVP，但产品主线仍是“知识库工具”，没有把项目理解、知识覆盖、技能差距和学习计划组织成一个可持续闭环。

2.0 需要把产品定位收束为面向个人开发学习的本地项目知识教练，同时避免在 1.x SQLite、向量索引和输出目录上原地演进造成数据污染。该决策在 2026-07-23 冻结目标架构；当时不代表 B-161～B-165 已实现，当前可达范围以[项目知识教练功能规格](../features/project-knowledge-coach.md)和源码测试为准。

## 2. 决策结论

### 2.1 产品主线

- 核心闭环为：导入代码项目与笔记 → 有来源的项目理解 → 学习问答 → 项目知识评估 → 通用技能差距 → 学习计划 → 用户确认后发布到 Obsidian。
- 项目知识覆盖是主评价口径；版本化通用技能树是辅助口径，只描述当前项目中被验证的语言、框架、数据、测试、交付和 AI 等能力。
- 禁止把项目内结果扩张为职业能力、求职评价或跨项目综合画像。
- 规则分析在无 LLM 时必须可运行；LLM 只增强摘要、题目和计划，不得生成无来源结论。

### 2.2 独立 v2 数据代际

- 2.0 默认数据根为 `runtime/v2/`，SQLite 为 `runtime/v2/app.db`；向量索引和日志使用同一代际下的独立位置。
- 1.x 的 `runtime/app.db`、向量/Qdrant 数据和输出文件不迁移、不删除、不覆盖，也不自动导入 2.0。
- 2.0 首次启动创建新库，用户重新导入项目。若目标路径被识别为 1.x schema 或旧向量目录，必须停止写入并报告配置错误。
- 旧数据只用于原版本回退或人工归档；未来若需要迁移，必须另立 ADR 和显式迁移工具。

当前实现已由 B-169 将问答结果导出默认目录对齐为活动 `<runtime>/outputs/`，本地默认是 `runtime/v2/outputs/`；`KI_OUTPUT_DIR` 和 `RAG_OUTPUT_DIR` 仍可显式覆盖。SQLite 备份脚本只备份数据库，导出文件与 Qdrant local 数据仍需按实际范围单独纳入备份。

### 2.3 Coach 领域模型

- 项目分析运行、稳定知识点、来源快照、版本化技能树、知识点—技能映射、评估会话、学习计划分别建模。
- 每个知识点、映射、评估结论和学习任务必须关联真实来源；来源内容、路径或 checksum 变化后，依赖分析标记为 `stale`。
- 首版优先结构化分析 Python、JavaScript/TypeScript 和常见 Web 清单；其他文本项目使用目录、清单、文档和 RAG 通用回退。
- 评估状态统一为 `unassessed / needs_work / developing / mastered`；边界依次为无有效结果、`< 0.50`、`0.50–0.74`、`>= 0.75`。
- 重新生成学习计划只创建新草稿，不覆盖已确认计划。

### 2.4 兼容边界

- 现有导入、聊天和 `/api/assessment/*` 契约继续保留，2.0 前端通过新增 Coach API 使用新领域模型。
- 当前实现状态由功能规格、统一设计文档和测试描述；本 ADR 记录 Accepted 决策边界，不作为完成度证明。
- 不恢复旧 PySide6 桌面实现，不引入多用户、团队空间、云同步或 Agent 写代码。

## 3. 备选方案

### 3.1 在 1.x 数据库原地加表

- 优点：路径和配置改动少，可直接复用现有项目数据。
- 缺点：新旧知识点、评估状态和发布修订语义混杂；回滚困难，存在 schema 与向量索引污染风险。
- 未采用原因：不满足“旧数据不迁移、不删除”和可安全回退要求。

### 3.2 自动迁移 1.x 项目

- 优点：用户无需重新导入。
- 缺点：现有资料不足以可靠生成稳定知识点与来源快照；迁移失败会产生真假难辨的半成品。
- 未采用原因：2.0 允许从零建立有来源的数据基线，安全性优先。

### 3.3 建立跨项目职业能力画像

- 优点：可形成更广泛的学习/求职建议。
- 缺点：超出当前证据范围，容易把单项目评估误作个人总体能力。
- 未采用原因：偏离个人项目学习闭环，也扩大隐私和解释责任。

## 4. 影响

| 模块 | 目标影响 |
|------|----------|
| 配置与存储 | 新增独立 v2 数据根和 Coach/Obsidian schema；禁止自动迁移 |
| 业务层 | 新增 Coach 分析、评估、覆盖聚合和学习计划领域 |
| API | 新增 `/api/coach/*`；旧契约保持兼容 |
| Vue | 导航收束为教练、学习地图、学习计划、资料、设置 |
| 文档与发布 | 目标版本为 `v2.0.0`，B-161～B-165 分片实现并验收 |

## 5. 风险与约束

- 目标能力在完成代码、测试和发布门禁前不得标记为当前实现。
- 所有结论必须可追溯到项目来源；LLM 文本不能成为唯一证据。
- v2 写路径必须与 1.x 物理隔离，发布验收需证明旧运行时文件未变化。
- 技能聚合必须保留“未验证”和“评估较弱”的差异。

## 6. 回滚策略

- B-161～B-165 未完成前，继续运行 1.x 当前入口和数据根。
- 2.0 实现出现问题时停止 v2 进程并回退到 1.x 版本；由于旧数据未被修改，无需反向迁移。
- v2 数据只能作为独立目录归档或由用户显式删除，不在回滚脚本中自动清理。

## 7. 验证方式

- 验证 2.0 首次启动只创建 `runtime/v2/`，旧 SQLite、向量索引和输出文件 hash 不变。
- 使用 Python、Vue/TypeScript 和通用文本夹具验证稳定知识点、真实来源、技能映射和无 LLM 回退。
- 验证来源修改、重命名、删除后分析进入 `stale`，重新分析产生新运行而不改写历史快照。
- 验证评估阈值、技能聚合、计划草稿与确认版本的不可覆盖约束。
- 验证旧导入、聊天和 `/api/assessment/*` 契约保持可用。
