# 文档写作规范

> 状态：Active
> Owner：RAG 团队
> Last Updated：2026-07-31
> Scope：Knowledge Island 活动文档、复用模板、过程记录和历史文档的统一写作规则
> Related：`README.md`、`../template-mapping.md`、`../.docs-template/state.tsv`

本文档定义本仓库文档的统一写作规则。目标是避免“已实现内容”和“规划内容”混写，以及不同文档使用不同语气导致的维护成本。

## 1. 基本原则

- 文档先结论：先写“当前结论/边界”，再写细节实现。
- 一文一主题：一篇文档只承担一个职责。
- 已落地与规划分离：正式文档默认只写当前 `v2.0.0` 已实现行为和仍有效的 1.x 兼容基线；未来考虑、候选方案和待验证点写入 `BACKLOG.md`，重大架构决策写入 ADR。
- 标题与术语统一：同一语义必须说明所处语境；当前用户界面使用“工作区”，后端/API/数据库继续使用 `project` / `project_id`，历史文档中的“项目空间”视为同一概念。

`Active` 表示文档结论当前有效。不得用“现已支持”“用户可以”等完成态措辞描述尚未落地的能力；需要同时说明当前与历史时，必须明确写成“当前 v2.0.0 / 1.x 兼容基线 / Archived 历史”，不得再把 v2.0.0 写成未来目标。

## 2. 文档头部模板（除 `CHANGELOG.md` 外）

```text
# 标题

> 状态：Draft / In Review / Active / Deprecated / Archived
> Owner：RAG 团队
> Last Updated：YYYY-MM-DD
> Scope：可选，按文档粒度填写
> Related：可选，相关文档路径
```

## 3. 占位符规范

复用模板中需要使用者替换的内容统一写成 `{{PLACEHOLDER_NAME}}`。活动文档除解释占位符语法的本文件外，不得保留双花括号 token。

### 3.1 命名规则

- **必须**使用双花括号：`{{NAME}}`。
- **必须**使用大写字母、数字和下划线组成的 `SCREAMING_SNAKE_CASE`，例如 `{{PROJECT_NAME}}`、`{{API_VERSION}}`。
- **必须**语义明确；禁止使用 `{{X}}`、`{{TODO}}` 等无信息名称。
- **禁止**混用 `[xxx]`、`<xxx>`、`{{xxx}}` 或全角括号表示待替换内容。
- `text` 代码块中的 ASCII 图可以用 `[区域名称]` 表示框体；这类内容不是占位符。
- GitHub Actions 的 `${{ github.sha }}` 属于工作流表达式，不是文档模板 token。

### 3.2 必填、可选与未知事实

- 默认占位符为必填；可选字段必须在行末或说明列标注 `（可选）`。
- 条件必填字段必须标注条件，例如 `（涉及架构决策时必填）`。
- 活动文档中的未知事实写为 `TBD`，明确不适用写为 `N/A`；禁止编造内容来消除占位符。

```markdown
> Owner：{{OWNER}}
> Reviewer：{{REVIEWER}}（可选）
> Related ADR：{{ADR_ID}}（涉及架构决策时必填）
```

### 3.3 活动文档与复用模板边界

- `.docs-template/state.tsv` 中 `placeholder_policy=preserve-template` 的文件可以保留合法 token；当前包括 ADR、RFC、DevLog、Postmortem、Feature、Plan 和各类 Guide 模板，以及本写作规范中的语法示例。
- 实际创建文档时，应复制对应模板并重命名，再把 token 替换为真实内容；不得直接把复用模板改成某一次任务的活动文档。
- 初始化器只替换已声明的项目级元数据，不猜测接口、账号、业务规则或技术决策。
- 严格门禁激活后，活动文档中的未替换 token、残缺 token 和非法命名会使检查失败。

常用 token：

| Token | 含义 | 示例值 |
|-------|------|--------|
| `{{PROJECT_NAME}}` | 项目名称 | `Knowledge Island` |
| `{{OWNER}}` | 责任人 | `RAG 团队` |
| `{{CURRENT_DATE}}` | `YYYY-MM-DD` 日期 | `2026-07-31` |
| `{{CURRENT_LOCAL_DATETIME}}` | 本地日期时间 | `2026-07-31 16:30` |
| `{{CURRENT_ISO_WEEK}}` | ISO 周 | `2026-W31` |
| `{{ADR_ID}}` | ADR 编号 | `ADR-010` |
| `{{RELEASE_VERSION}}` | 发布版本 | `v2.0.0` |

## 4. 章节结构

推荐顺序：

1. 目的 / 背景
2. 范围 / 边界
3. 结论 / 规则
4. 行为细节
5. 示例 / 附录（如有）

## 5. 命名与样式

- 文件名使用小写 `kebab-case`。
- 同一文档中优先使用短句，避免重复否定。
- 中文文档使用全角中文标点，代码、命令、变量名保留半角。
- 状态词汇统一使用：
  - **必须**：不允许偏离
  - **应该**：建议执行，可在文内说明例外
  - **可选**：按场景实施
  - **禁止**：明确不应出现

### 5.1 前端术语

| 语境 | 推荐用词 | 说明 |
|------|----------|------|
| 普通用户界面 | 工作区、添加资料、回答依据、回答引擎、工具 | 避免直接暴露内部实现术语 |
| 后端、API、数据库 | `project`、`project_id`、`session_id` | 代码与契约不因界面文案变化而重命名 |
| 历史文档 | 项目空间 | 表示与“工作区”相同的用户概念；新设计文档应优先使用“工作区” |
| 当前聊天文案 | 线程 / 会话 | 侧栏统计仍使用“线程”，会话管理组件使用“会话”；修改任一文案时必须同步前端代码、功能文档和测试 |
| 当前一级入口 | 教练、学习地图、学习计划、资料、设置 | `v2.0.0` 已落地的信息架构；资料是模态入口，评估是覆盖层而非一级入口 |
| 当前评估 | 开始评估、评估结果、评估记录 | 结论必须限定为“当前项目中的评估结果”，不代表整体职业能力 |
| Obsidian 一次性导入 | 导入 Obsidian Vault | 兼容的只读导入能力，不等同于插件连接或持续同步 |
| Obsidian 插件 | 连接 Obsidian、预览发布、确认发布、同步冲突 | 已实现增量来源同步和受控发布；`queued` 不等于 `applied`，冲突时不得覆盖用户笔记 |

## 6. 链接与图示

- 文档内交叉链接优先使用相对路径（如 `design/architecture-overview.md`）。
- 外部链接带完整协议，尽量附来源日期。
- 页面结构和架构关系尽量用文本图 + 表格，复杂关系可用 Mermaid。

## 7. 文档维护

- 文档行为改动必须同步：
  - `requirements/*`（已落地边界）
  - `design/*`（架构与数据）
  - `guides/testing.md`（验证方式）
  - `BACKLOG.md`（未完事项）
  - `CHANGELOG.md`（对外变更）
- `docs/README.md` 的目录说明与实际文件必须保持一致。
- 产品代际发生变化时，入口 README、需求、设计、ADR、BACKLOG 和发布说明必须使用同一组“当前 / 目标 / 历史”边界。
