# Knowledge Island 2.0 用例定义

> 状态：Active
> Owner：RAG 团队
> Last Updated：2026-07-23
> Scope：项目知识教练目标用例
> Related：docs/requirements/project-background-and-scope.md, docs/features/project-knowledge-coach.md

## 1. 状态说明

以下为 2.0 目标用例，不表示当前 1.x 已经实现。1.x 的项目导入、问答、评估和 Obsidian vault 一次性导入继续作为兼容基线。

## 2. 主要用户场景

### UC-01 创建工作区并导入项目

- 用户在全新 v2 数据根中创建工作区，导入代码目录、项目文档和笔记。
- 系统按项目隔离资料，并为每个可用来源保留路径、类型和内容版本。
- Python、JavaScript / TypeScript 和常见 Web 清单进入优先分析路径；其他文本项目进入通用回退。
- 单文件失败不得阻断其他文件处理，失败原因必须可见。

### UC-02 生成有来源的项目理解

- 用户发起项目分析。
- 系统生成项目概览、稳定知识点和通用技能映射，并为每项结果返回真实来源。
- 无 LLM 时使用目录、清单、文档、测试路径和规则基线；有 LLM 时只增强表达和提炼。
- 资料不足时系统保留未知项，不得补造模块、技术栈或实现事实。

### UC-03 进行学习问答

- 用户在“教练”中围绕当前项目提问，系统复用聊天、流式回答和依据抽屉。
- 回答必须展示来源；上下文不足时明确提示补充资料或重新分析。
- 切换工作区后，会话、来源、评估和计划都切换到对应项目。

### UC-04 发起定向评估

- 用户从知识点、技能节点或聊天工具入口发起评估。
- 系统创建可恢复的评估会话，问题只使用当前项目的真实来源。
- 作答前不返回评分依据；作答后保存规则或模型评估方式、置信度、命中证据、缺失点和来源。
- 结果归一为 `unassessed / needs_work / developing / mastered`。

### UC-05 查看项目覆盖与技能差距

- 用户在“学习地图”查看项目知识覆盖、通用技能映射和评估记录。
- 项目知识覆盖是主视图；技能树状态只能由关联知识点聚合。
- 界面必须区分“尚未验证”和“已经评估但较弱”，并提示结果仅代表当前项目。
- 用户可从任一知识点或技能节点查看来源并再次发起评估。

### UC-06 生成并确认学习计划

- 用户根据当前差距生成学习计划草稿。
- 每个任务包含学习目标、关联知识点或技能、阅读来源、练习问题、完成标准、预计时长和状态。
- 用户可编辑和排序草稿；确认后形成不可被重新生成覆盖的版本。
- 再次生成只创建新草稿，不替换已确认计划。

### UC-07 连接 Obsidian 并同步来源

- 用户在桌面版 Obsidian 插件中使用一次性限时配对码连接一个项目。
- 插件批量发送 Markdown 的新增、修改、重命名和删除事件，以及 Frontmatter、标签和 Wikilink 元数据。
- 重复事件不产生重复数据；重命名保留来源映射；删除清理来源索引并使相关分析过期。
- 系统管理的输出目录不再反向摄入，避免同步反馈循环。

### UC-08 预览并发布到 Obsidian

- 用户在 Knowledge Island 中预览发布内容和目标路径，再显式确认。
- 插件只在授权目录内更新带系统管理标记且哈希未冲突的文件。
- 无管理标记、外部修改、越界路径或插件离线时停止写入并返回冲突或失败状态。
- 系统保存不可变发布修订；被用户删除的生成文件不自动重建。

### UC-09 来源变化后恢复可信状态

- 来源内容变化、删除或同步后，与之相关的项目分析标记为 `stale`。
- 过期结果仍可追溯到原修订，但不得伪装为最新结论。
- 用户重新分析后生成新结果，既有评估和已确认计划不被静默覆盖。

## 3. 全局需求约束

- 普通用户界面使用“工作区”；后端、API 和数据库继续使用 `project` / `project_id`。
- 项目知识结论没有来源时必须省略或标记未知。
- 通用技能差距不扩张为职业、求职、绩效或跨项目评价。
- 网络服务仅用于用户主动配置的模型调用或既有受控导入；LLM 不得成为闭环必需条件。
- 2.0 只写入 `runtime/v2/`，不得迁移或修改旧运行时数据。
- Obsidian 写回始终经过预览和显式确认，不得覆盖用户自有笔记。
