## 2. 项目背景

个人开发者和编程学习者通常同时维护代码、架构说明、需求记录、测试、调试笔记和 Obsidian 笔记。现有本地知识库能够帮助检索资料，却难以持续回答以下问题：

- 我是否真正理解当前项目的关键结构、流程和约束？
- 哪些项目知识已经验证，哪些仍然缺少理解证据？
- 当前项目反映出哪些通用技术能力需要补强？
- 下一步应该阅读什么、练习什么，以及如何判断已经完成？

Knowledge Island 2.0 因此从“通用本地 AI 第二大脑”转向“面向个人开发学习的本地项目知识教练”。系统仍以 RAG、来源引用和本地优先存储为基础，但产品主线改为围绕一个真实项目建立可验证的学习闭环。

## 3. 产品定位

### 3.1 核心闭环

```text
导入代码项目与笔记
  -> 生成有来源的项目理解
  -> 基于项目资料学习问答
  -> 评估项目知识
  -> 查看项目知识覆盖与通用技能差距
  -> 生成、编辑并确认学习计划
  -> 经用户确认后发布到 Obsidian
```

### 3.2 产品原则

- **项目知识优先**：评价对象是用户对“当前项目”的理解，不建立脱离项目证据的泛化能力画像。
- **来源可追溯**：项目理解、知识点、技能映射、评估反馈和学习任务必须能回到真实项目来源。
- **学习而非求职评价**：通用技能树用于组织学习差距，不输出职业等级、岗位匹配度或录用建议。
- **本地规则可独立工作**：不配置 LLM 时也必须能够完成基础分析、问答回退、规则评估和计划生成。
- **LLM 只做可选增强**：配置模型后可以增强摘要、问题和学习建议，但不得移除来源约束或把模型推断伪装为项目事实。
- **发布由用户控制**：任何写回 Obsidian 的内容都必须经过预览和显式确认。

## 4. 目标用户与场景

| 用户类型 | 主要诉求 | 典型场景 |
|----------|----------|----------|
| 独立开发者 | 快速恢复和验证对项目的理解 | 接手旧项目，梳理模块、接口、测试和关键约束 |
| 编程学习者 | 用真实项目检验学习成果 | 完成 Python、Vue 或 TypeScript 项目后发现知识盲区 |
| 个人技术知识管理者 | 连接项目资料与长期笔记 | 将 Obsidian 笔记纳入项目理解，并把确认后的学习成果发布回 vault |

2.0 不面向团队绩效考核、招聘筛选、企业知识治理或跨成员能力排名。

## 5. 2.0 目标范围

### 5.1 纳入范围

- 导入代码项目、项目文档和笔记，并继续提供有来源的检索与问答。
- 生成项目概览、知识点和知识点之间的来源关联。
- 针对 Python、JavaScript / TypeScript 和常见 Web 项目清单提供优先结构化分析。
- 对其他文本型项目提供基于目录、清单、文档和 RAG 的通用回退，不因语言未专门支持而阻断闭环。
- 从知识点或通用技能节点发起持久化评估，保存回答、评分结果、置信度和来源。
- 以项目知识覆盖为主视图，以版本化通用技能树为辅助视图。
- 生成可编辑、排序和确认的学习计划；确认后的计划不被重新生成操作覆盖。
- 通过桌面版 Obsidian 配套插件接收 Markdown 变更事件，并受控发布项目理解、差距、学习计划和评估记录。
- 保留现有聊天、来源抽屉、资料入口和高级检索 / 模型 / Agent 审计能力，但将高级能力收起。

### 5.2 数据代际

- 2.0 默认使用全新 `runtime/v2/` 数据根，从零创建项目和教练数据。
- 不迁移、不删除、不覆盖 1.x 的 `runtime/app.db`、向量目录和输出文件。
- 用户需要在 2.0 中重新导入项目；不承诺 1.x 与 2.0 之间的数据合并或跨项目能力汇总。

### 5.3 当前 1.x 兼容基线

当前 1.x 已具备项目隔离、资料导入、RAG 问答、来源展示、会话、规则化评估和 Obsidian vault 一次性只读导入等能力。2.0 必须保持以下边界：

- 现有 `/api/import/obsidian-vault` 继续表示用户手动触发的一次性只读导入，不等同于插件连接或双向同步。
- 现有导入、聊天和 `/api/assessment/*` 接口继续作为兼容契约；2.0 前端使用新的 Coach 接口承载新闭环。
- 旧运行时数据保持原样，2.0 不以迁移脚本或隐式升级修改它。

## 6. 评价口径

### 6.1 项目知识覆盖

项目知识覆盖是主评价口径。覆盖状态统一为：

- `unassessed`：尚无评估证据。
- `needs_work`：得分低于 `0.50`。
- `developing`：得分为 `0.50–0.74`。
- `mastered`：得分不低于 `0.75`。

这些状态只描述用户在当前项目、当前来源版本下的评估结果。

### 6.2 通用技能树

通用技能树用于把项目知识映射到语言、框架、数据、测试、交付、AI 等可复用学习主题。它必须遵守：

- 技能状态由关联的项目知识点聚合，不凭空生成。
- “未验证”与“评估较弱”必须分开表达。
- 不生成跨项目总分、职业等级、岗位胜任力或个人排名。
- 没有来源或映射证据时，不得宣称用户具备或缺失某项技能。

## 7. 非目标

- 多用户、团队空间、云同步或跨设备协同。
- 职业能力模型、JD 匹配、求职评价、绩效考核或证书体系。
- 跨项目能力总览、跨项目资料共享或全局资料库。
- 移动端 App、Obsidian 移动端插件或社区市场发布。
- 日历排期、提醒系统或自动安排学习时间。
- 完整 AST 调用图、全语言静态分析器或 IDE 替代品。
- 让 Agent 写代码、执行 shell 或修改项目文件。
- 无需用户确认的 Obsidian 自动写回，以及对非系统管理笔记的覆盖。
- 将 LLM 设为必需依赖，或在无来源时用模型补造项目事实。

## 8. 2.0 成功标准

| 维度 | 验收目标 |
|------|----------|
| 闭环完整性 | 固定样例可完成“导入 → 分析 → 问答 → 评估 → 差距 → 计划 → Obsidian 发布” |
| 来源约束 | 项目知识点、技能映射、评估结论和学习任务均能返回真实来源；来源不足时明确降级 |
| 语言覆盖 | Python、JavaScript / TypeScript 样例使用结构化分析，通用文本样例能通过回退流程完成闭环 |
| 离线可用 | 未配置 LLM 时仍可完成基础分析、规则评估和计划生成 |
| 兼容安全 | 旧运行时目录内容不被迁移、删除或修改；旧 API 兼容契约继续存在 |
| 发布安全 | Obsidian 写回经过预览、确认和插件执行；冲突或越界路径被阻断 |

## 9. 约束条件

- **人力约束**：单人开发，优先复用现有 FastAPI、Vue、SQLite、RAG 和 Tauri 能力。
- **运行约束**：本地优先；联网仅用于用户主动配置的模型调用或现有受控网络导入。
- **隐私约束**：项目内容默认保留在本机；调用外部模型时必须明确由用户配置并遵守现有密钥保护规则。
- **安全约束**：API Key、配对令牌等敏感值不得明文持久化或通过普通接口回显。
- **复杂度约束**：首版只为 Python、JavaScript / TypeScript 和常见 Web 清单提供专门规则，其他类型使用通用回退。
