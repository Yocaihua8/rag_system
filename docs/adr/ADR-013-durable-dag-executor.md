# ADR-013 SQLite 持久化 DAG 执行器

> 状态：Accepted
> Date：2026-08-02
> Owner：RAG 团队
> Scope：v3 工作流版本、步骤调度、并发、重试和重启恢复
> Related：`../design/agent-runtime-and-tool-contract.md`、`ADR-002-sqlite-storage.md`、`ADR-012-agent-product-and-permissions.md`

## 1. 背景

FastAPI `BackgroundTasks`、浏览器 SSE 连接或单纯的内存协程都不能在应用重启后恢复任务，也无法可靠表达租约、审批等待和不确定写结果。首版又只有本机单服务进程、两并发和手动触发，不需要引入外部队列控制平面。

## 2. 决策结论

- 使用 SQLite 保存工作流定义/不可变版本、任务、运行、步骤、尝试、租约、事件、审批和产物。
- FastAPI lifespan 启动持久调度循环；HTTP 只提交状态，不直接执行任务。
- 全局最多两个读取/分析槽；同一项目写步骤通过数据库事务串行。
- 等待审批释放执行槽；读取/分析最多自动重试两次。
- 写步骤开始后不自动重放；重启发现结果不明确时进入 `recovery_required`。
- 状态和 append-only 事件在同一事务提交，SSE 通过持久序号续传。

## 3. 决策原因

1. SQLite 与当前本地单进程形态一致，部署和备份成本最低。
2. 持久状态能够把崩溃恢复从 UI/内存细节变成可测试的领域行为。
3. 明确区分读取重试和写入恢复，避免重复外部副作用。
4. 两并发规模不需要 Redis、Celery 或独立编排服务。

## 4. 备选方案

### 4.1 FastAPI BackgroundTasks / 内存队列

- 优点：实现简单。
- 缺点：进程退出即丢失，无法安全租约、恢复或审计。
- 未采用原因：不满足正式产品的恢复要求。

### 4.2 Redis + Celery / Temporal / Prefect

- 优点：成熟的分布式执行和监控能力。
- 缺点：引入额外服务、部署、升级和桌面打包负担。
- 未采用原因：当前本地单用户规模不需要分布式控制平面。

## 5. 影响

### 5.1 正面影响

- 暂停、取消、重试、审批和重启恢复可以由数据库事实驱动。
- SSE 断线不会丢失任务进度。

### 5.2 负面影响

- Schema、事务和恢复测试复杂度明显增加。
- SQLite 版本保持单服务进程，不支持多 Uvicorn worker 水平扩展。

### 5.3 对现有系统的改动点

- 新增 workflow/application/worker/infrastructure 边界。
- 新增 WAL、busy timeout、租约和 `BEGIN IMMEDIATE` 事务策略。

### 6.2 回滚策略

| 项目 | 内容 |
|------|------|
| 回滚触发条件 | 租约、恢复或写操作幂等测试不通过 |
| 回滚步骤 | 不启用 v3 executor 和路由；继续运行独立 v2 后端 |
| 数据回滚说明 | 删除未投入使用的 v3 数据根；不修改 v2 数据 |
| 回滚责任人 | RAG 团队 |
| 不可回滚的点 | 已由用户确认并写入外部系统的副作用 |

### 6.3 验证方式

- 覆盖并发上限、同项目写串行、租约过期、暂停/取消、审批释放槽和崩溃恢复。
- 断开并重连 SSE 后事件无缺失、无重复展示。
- 不确定写步骤不会自动重新执行。

### 6.4 待办项

- 多进程或多用户需求出现时重新评估 PostgreSQL 和外部队列。
