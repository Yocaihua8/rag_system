## 2. 功能目标

项目知识教练把当前项目的代码、文档和笔记转为可验证的学习对象，帮助用户完成：

```text
项目输入 -> 有来源的理解 -> 学习问答 -> 项目评估
        -> 知识覆盖与技能差距 -> 学习计划 -> Obsidian 发布
```

主评价对象是“用户对当前项目知识的理解”。通用技能树只用于归类和组织学习差距，不构成跨项目能力档案、职业能力分数或求职评价。

## 3. 核心业务对象

| 对象 | 业务含义 |
|------|----------|
| 项目 | 一组相互隔离的代码、文档、笔记及教练数据；界面称“工作区” |
| 来源 | 支撑结论的真实文件、片段或导入记录 |
| 分析运行 | 针对某一来源版本生成项目理解的过程，可为最新或 `stale` |
| 知识点 | 用户需要理解的项目事实、流程、约束或代码定位，具有稳定标识和来源 |
| 技能节点 | 语言、框架、数据、测试、交付、AI 等通用学习主题 |
| 评估会话 | 针对知识点或技能节点的一组可恢复问题、回答和结果 |
| 学习计划 | 从项目差距生成、可编辑并由用户确认的版本化任务列表 |
| Obsidian 发布 | 经预览和确认后由插件写入系统管理 Markdown 的不可变修订 |

## 4. 项目分析契约

### 4.1 分析策略

- B-161 已对 Python、JavaScript / TypeScript、`package.json`、`pyproject.toml`、requirements、TypeScript / Vite、Docker / Compose 等常见清单启用首批专门规则。
- 其他文本项目使用已入库的 README、目录和高信号文档通用回退；分析器不绕过导入层直接扫描磁盘。
- 无 LLM 时，规则基线已经能够生成基础项目概览、稳定知识点和有来源的技能映射。
- 有 LLM 时，B-161 只允许增强项目概览摘要；知识点、技能映射和来源仍由规则确定。模型失败返回规则结果和 warning。

### 4.2 来源规则

- 每个项目结论、知识点和技能映射必须至少关联一个真实来源。
- B-161 存储层要求来源解析到同项目已导入文档或分块，并以数据库中的相对路径和 checksum 为准，拒绝调用方伪造路径或哈希。
- 没有足够来源时，结果必须标记未知或省略，不得由模型补造。
- 来源内容变化或删除后，相关分析必须标记为 `stale`。
- 来源重命名应保留文档映射；删除来源应清理对应索引。
- 重新分析生成新运行，不静默改写历史分析、评估或已确认计划。
- B-161 已在文档新增、修改、删除及 GET 指纹复核时把受影响分析标为 `stale`；来源快照在原文档删除后仍保留相对路径、哈希、摘录和定位。

## 5. 评估与覆盖契约

### 5.1 发起与作答

- 评估可从知识点、技能节点或教练输入工具发起。
- 评估会话必须持久化并可恢复，不固定使用第一份文档或固定三道题。
- 作答前只返回题目和必要上下文，不返回参考答案、评分关键词或评分依据。
- 作答后记录 `rule|model` 评估方式、分数、置信度、命中证据、缺失点和来源。
- 模型不可用或结果不可验证时回退为规则评估，并明确低置信度。

### 5.2 状态与阈值

| 状态 | 规则 | 用户含义 |
|------|------|----------|
| `unassessed` | 没有有效评估 | 尚未验证 |
| `needs_work` | 得分 `< 0.50` | 当前项目中需要补强 |
| `developing` | 得分 `0.50–0.74` | 当前项目中正在形成理解 |
| `mastered` | 得分 `≥ 0.75` | 当前项目中已有较充分证据 |

所有界面必须说明：结果只代表当前项目、当前来源版本下的评估，不代表用户整体技术能力。

### 5.3 双层差距

- 项目知识覆盖是主视图，逐知识点展示状态、来源和最近评估。
- 通用技能树是辅助视图，状态只由关联项目知识点聚合。
- “未验证”不得与“评估较弱”合并。
- 技能节点没有知识点映射时保持无项目证据，不得判断为掌握或缺失。
- 禁止输出跨项目总分、职业等级、JD 匹配、求职建议、绩效或排名。

## 6. 学习计划契约

- 计划由当前项目知识覆盖和技能差距生成。
- 每个任务必须包含目标、关联知识点或技能、阅读来源、练习问题、完成标准、预计时长和状态。
- 草稿可编辑和排序，确认后形成独立版本。
- 再次生成只创建新草稿，不覆盖已确认计划。
- 来源不足时可以生成“补充资料”任务，但不得伪造阅读来源。
- 确认学习计划不等于发布；发布到 Obsidian 仍需单独预览和确认。
- 首版不提供日历排期、提醒、自动执行或证书。

## 7. Obsidian 协作边界

### 7.1 输入

- 现有 `/api/import/obsidian-vault` 保持一次性只读导入语义。
- 2.0 目标通过独立桌面插件接收 `upsert / rename / delete` 幂等事件。
- 插件可以发送 Frontmatter、标签、已解析和未解析 Wikilink；系统管理输出目录不反向摄入。
- 每个项目最多一个活动连接，配对令牌限时、可撤销且服务端只保存哈希。

### 7.2 输出

默认发布目录为 `Knowledge Island/<项目名>/`，可在配对时修改。目标产物包括：

- `项目理解.md`
- `知识覆盖与技能差距.md`
- `学习计划.md`
- `评估记录/<时间>.md`

发布必须经过“内容与路径预览 → 用户确认 → 插件执行 → 结果回传”。可更新文件必须带 `knowledge_island_managed`、稳定 ID、项目 ID、产物类型和修订号。

以下情况必须停止覆盖并返回冲突：

- 目标文件没有系统管理标记。
- 文件哈希自上次修订后变化。
- 目标路径超出授权输出目录。
- 插件离线、令牌失效或项目连接已撤销。

首版不自动合并冲突。被用户删除的生成文件不自动重建；系统保留不可变发布修订用于追溯和回滚。

## 8. Vue 体验契约

- 一级入口为“教练 / 学习地图 / 学习计划 / 资料 / 设置”。
- “教练”复用现有 Codex 风格侧栏、会话、流式回答和依据抽屉。
- “学习地图”展示项目理解、知识覆盖、技能差距和评估记录，节点可查看来源并发起评估。
- “学习计划”提供草稿编辑、排序、确认、发布预览和冲突处理。
- 评估使用抽屉或覆盖层，从输入工具或学习地图进入，不恢复管理后台式独立页面。
- “资料”和“设置”展示真实 Obsidian 配对、目录、令牌撤销和同步状态，不伪装连接成功。
- 高级检索、模型比较和 Agent 审计继续收在高级区域。

## 9. 数据与兼容契约

- 2.0 默认数据根为 `runtime/v2/`，用户需要重新导入项目。
- 不提供 1.x 数据迁移、合并或跨项目能力汇总。
- 旧 `runtime/app.db`、向量目录和输出保持原样。
- 现有导入、聊天和 `/api/assessment/*` 契约继续保留；新闭环使用 Coach 和 Obsidian API。
- 敏感令牌、API Key 或密码不得明文持久化或在普通响应中返回。

## 10. 验收标准

- Python、JavaScript / TypeScript 和通用文本样例都能生成有来源的项目理解。
- 未配置 LLM 时规则基线可完成分析、评估、差距和计划；LLM 失败时可受控回退。
- 知识点定向评估可恢复，评分依据在作答前不可见，结果包含评估方式、置信度、证据、缺失点和来源。
- 项目覆盖与技能树正确区分 `unassessed` 和低分状态，并展示“仅限当前项目”的说明。
- 新计划草稿不覆盖已确认版本。
- Obsidian 重复事件、重命名、删除、离线重放和输出目录排除有确定行为。
- 发布可完成预览、确认、执行和结果回传；无标记文件、哈希冲突和路径越界均被阻断。
- 端到端闭环通过后，旧运行时目录仍保持不变。

## 11. 非目标

- 团队空间、多用户、云同步、跨项目知识或能力汇总。
- 职业能力、JD 匹配、求职评价、绩效考核或个人排名。
- 移动端、Obsidian 移动插件或社区市场发布。
- 完整 AST 调用图、全语言静态分析、IDE 或 Agent 编码。
- 日历排期、提醒、证书和无需确认的自动发布。
- 修改无系统管理标记的 Obsidian 用户笔记。
