本文档定义维护者、贡献者和使用者如何参与决策、获得权限和处理分歧。小型或单维护者项目可以保持简洁，但决策权和升级路径不能依赖口头约定。

## 2. 角色与权限

| 角色 | 职责 | 可执行操作 | 产生方式 |
|------|------|------------|----------|
| 维护者 | 路线图、合并、发布（如有）、安全协调 | 合并变更、管理事项、按需发布版本 | {{MAINTAINER_SELECTION_RULE}} |
| Reviewer | 评审指定模块或主题 | Review、建议合并或退回 | {{REVIEWER_SELECTION_RULE}} |
| 贡献者 | 提交 Issue、代码、文档或测试 | 按贡献指南参与 | 完成被接受的贡献 |
| 使用者 | 使用项目并反馈问题 | 提交 Issue / Discussion | 无需额外权限 |

代码托管平台权限只是执行手段，不等同于永久治理权。实际维护者名单和权限范围应有可审计记录。

## 3. 决策方式

| 决策类型 | 默认方式 | 决策人 | 记录位置 |
|----------|----------|--------|----------|
| 小型修复与文档调整 | PR Review 后合并 | 模块维护者 | PR |
| 新功能与行为变化 | Issue / 功能文档明确范围后实施 | 维护者 | Issue + PR |
| 重大架构或兼容性变化 | RFC / ADR 评审 | {{ARCHITECTURE_DECISION_OWNER}} | RFC + ADR |
| 安全事件 | 私密渠道协调，修复后按需披露 | 安全负责人 | 安全事件记录 |
| 许可证或治理变化 | 公开提案并保留评议窗口 | 核心维护者 | RFC / Governance PR |

默认以形成可执行结论为目标，而不是追求全员一致。若无法达成结论，按 § 4 的升级路径处理。

## 4. 分歧与升级路径

1. 先在原 Issue 或 PR 中明确争议点、事实依据和可选方案。
2. 由对应模块维护者给出初步结论。
3. 涉及跨模块、兼容性、安全或社区规则时，升级给核心维护者。
4. 仍无法处理时，记录暂缓原因、重新评估条件和下一次复核日期。
5. 行为规范或安全问题不得在公开线程披露受害者信息、密钥或未修复漏洞细节。

## 5. 维护者加入、退出与继任

| 场景 | 规则 |
|------|------|
| 新增维护者 | 持续贡献达到 {{MAINTAINER_ELIGIBILITY_RULE}}，经 {{APPROVAL_RULE}} 确认 |
| 权限扩大 | 先限定模块或发布权限，经过观察期后再扩大 |
| 主动退出 | 完成待办、发布权限、安全渠道和账号的交接 |
| 长期不活跃 | 连续 {{INACTIVE_PERIOD}} 无响应后，由其他维护者联系并记录处理结论 |
| 紧急撤权 | 出现账号泄露、滥用权限或明确安全风险时可先撤权再复核 |
| 项目无人维护 | 在 README 标明状态，寻找继任者，或按归档流程停止发布 |

## 6. 发布（如有）与安全权限

没有 Tag、Release、包仓库或自动发布流程时，将对应发布行标记为 `N/A`；不要为了补齐治理表而创建发布体系。启用 `release-support` pack 后，再把实际发布流程关联到 `release-process.md`。

| 权限 | 主负责人 | 备份负责人 | 最低保护措施 |
|------|----------|------------|----------------|
| 合并到默认分支 | TBD | {{BACKUP_MAINTAINER}} | Review / 分支规则 |
| 创建 Release / Tag | TBD | {{BACKUP_MAINTAINER}} | MFA、受控凭证、发布检查 |
| 包仓库发布 | {{PACKAGE_PUBLISHER}} | {{BACKUP_MAINTAINER}} | 最小权限、短期凭证或可信发布 |
| 安全公告 | TBD | {{BACKUP_MAINTAINER}} | 私密渠道、最小披露 |

不得把长期 Token、私钥或恢复码写入本文档。

## 7. 治理自查清单

- [ ] 当前维护者及其权限可查。
- [ ] 常规、重大、安全和许可证决策都有明确路径。
- [ ] 分歧升级和暂缓条件已经定义。
- [ ] 维护者加入、退出和无人维护时的处理方式已经定义。
- [ ] 实际存在的发布与安全权限至少有一名备份负责人，或明确记录单点风险；不存在的发布能力已标记 `N/A`。
- [ ] 治理规则与 CONTRIBUTING、CODE_OF_CONDUCT、SECURITY 保持一致。
